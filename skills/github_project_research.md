# GitHub 项目深度研究 Skill

本文件定义了针对 GitHub 项目进行深度研究并产出标准化研究报告的工作方式。

---

## 仓库结构

```
web_crawler/
├── reports/          # 所有研究报告，文件名格式：YYYYMMDD-[主题描述].md
├── templates/        # 报告模板
│   └── research_report_template.md
├── skills/           # 研究技能说明（本文件）
│   └── github_project_research.md
└── readme.md
```

---

## 研究工作流

收到"对 [GitHub 仓库 URL 或项目名] 进行研究"的任务时，按以下步骤执行：

### Step 1 — 获取项目基本信息

使用 GitHub MCP 工具获取：
- 仓库元数据（Stars、语言、License、最后更新）
- 最近 commit 列表（了解活跃程度）
- 仓库目录结构（根目录文件 + 1 层子目录）
- README 全文

### Step 2 — 深度代码分析

- 读取关键目录下的核心文件（入口文件、主要模块、配置文件）
- 识别技术栈、架构模式（MVC / 事件驱动 / 管道 / Agent 等）
- 找到核心算法或关键创新点
- 阅读 Issues / PRs 了解已知问题和未来方向

### Step 3 — 专项研究

根据任务要求，选择以下一种或多种专项分析角度：

| 角度 | 重点关注 |
|------|---------|
| **爬虫能力** | 抓取策略、反爬处理、动态页面支持、数据结构化方式 |
| **AI 集成** | LLM 调用方式、prompt 工程、输出校验、成本控制 |
| **检索能力** | 检索算法、召回率、精确率、多语言支持 |
| **架构质量** | 模块化程度、可扩展性、错误处理、测试覆盖 |
| **改进方案** | 识别痛点 → 提出具体可实施的改进方案（含代码示例） |

### Step 4 — 撰写研究报告

使用 `templates/research_report_template.md` 作为报告框架，填写各节内容：
- 保留所有章节标题，删除 `[方括号内的占位符]`
- 使用表格、代码块、ASCII 流程图等增强可读性
- 所有代码示例需真实可运行（或标注"示意代码"）
- 结论部分必须给出明确的后续行动清单

### Step 5 — 保存报告

将生成的报告保存至 `reports/` 目录，文件命名格式：

```
reports/YYYYMMDD-[项目名或主题描述].md
```

例如：
- `reports/20260301-ScrapeGraphAI深度分析.md`
- `reports/20260315-marathon_calendar爬虫改进.md`

## 报告质量标准

一份合格的研究报告需满足：

| 标准 | 说明 |
|------|------|
| **有据可查** | 所有技术结论均基于实际代码/文档，不猜测 |
| **可操作** | 改进建议需包含具体实现路径，不泛泛而谈 |
| **结构完整** | 使用模板中的所有一级章节 |
| **代码准确** | 示例代码与被研究项目的实际 API 保持一致 |
| **中文为主** | 报告正文使用中文，代码和专有名词保持英文 |

## 常用 GitHub MCP 工具速查

| 工具 | 用途 |
|------|------|
| `get_file_contents` | 读取仓库中的文件或目录 |
| `list_commits` | 查看最近提交，了解项目活跃度 |
| `list_issues` | 了解已知问题和社区反馈 |
| `list_pull_requests` | 了解进行中的功能开发方向 |
| `search_code` | 在仓库中搜索特定代码模式 |
| `get_commit` | 查看某次提交的具体变更 |

## 注意事项

1. **私有仓库**：若目标项目为私有仓库，仅凭公开信息（README、公开 Issues）进行分析，并在报告中注明
2. **代码版权**：报告中引用的代码片段须注明来源文件路径
3. **客观立场**：既写优点，也写不足，避免单纯的正面评价
4. **更新频率**：每次研究完成后及时提交报告；若研究同一项目有新发现，创建新的日期版本而非覆盖旧报告
